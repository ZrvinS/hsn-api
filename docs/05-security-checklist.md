# 05 — Security Checklist (HSN Rate API)

Status: binding for all code under `server/`. Subordinate to `00-coordinator-decisions.md`, `00b-coordinator-rulings.md` and `00c-coordinator-rulings-round2.md`. Round 2 applied the security review `reviews/security-docs-round1.md` (SA-D-01…26); the change map is `reviews/docs-fix-round2.md`.
Audience: the security auditor (reviews every code file against this list), implementers, validator.

## How to use this checklist

- Every item has an ID (`SEC-xx`), a requirement, a verification method, and a severity.
- Severity: **Critical** (block merge/release), **High** (block release), **Medium** (fix within the current milestone), **Low** (track).
- The auditor records each item per review as `PASS` / `FAIL` / `N/A (reason)` in `reviews/security-audit-*.md`, citing file:line evidence.
- "Test" means an automated vitest test that exists in `server/test/` and runs in CI. If a verification says "test", a missing test is itself a `FAIL`. Test IDs (`T-xx`) refer to `02-TRD.md` §15.
- Every verification is pass/fail. It names a test, a CI step with an empty-output criterion, or a document that must exist with named content. "Review" appears only where no automated check is possible, and then it names what the reviewer must see.
- Where a command is given, run it from `server/`.
- Numbering runs SEC-01…101 with no gaps. Round 2 added SEC-43…49 and SEC-91…101.

## 0. Threat model summary (what we protect)

| Asset | Why it matters | Main threats |
|---|---|---|
| Rate table + rate rules | Clients print these on GST invoices; a wrong rate means wrong tax for many businesses | Unauthorised/unreviewed change, tampering at rest, poisoned ingestion, unreviewed seed rates served for tax |
| Classification reference data (synonyms, category map, chapter keywords, HSN descriptions) | One curated synonym decides a `high` classification, and the rate follows the code | Unreviewed edits, poisoned external product data |
| API keys (client + admin) and admin identities | Gate usage, billing and admin writes; maker–checker depends on two real people | Leakage in logs/repos, brute force, slow revocation, one person minting a second identity |
| Audit log | Proof of who changed which rate and when | Deletion, mutation, gaps, wholesale rewrite |
| Service availability | Billing clients (e.g. Sunarone POS) call us at checkout | DoS via expensive search/classify/tax, outbound lookup amplification, LLM cost |
| Infrastructure reachability | Server makes outbound calls for barcodes, the CBIC watcher and notifications | SSRF into internal network / cloud metadata |
| Client request content | Product names may embed customer info | Logging PII, reversible hashes, sending to third-party LLMs |

**Residual risk (00c ruling 17, SA-D-01).** Maker–checker stops a single actor from changing rates **through the API**. It does not stop the host owner. Anyone with shell access to the host, or with write access to the DB file plus the key peppers (`HSN_KEY_PEPPER` / `HSN_KEY_PEPPERS`) and `HSN_AUDIT_KEY`, can bypass the whole application layer: drop triggers, edit rows, recompute the HMAC chain. The compensating controls detect this; they do not prevent it:
- the off-host audit head (SEC-97);
- `rule_sha256` for each approved rule (SEC-53);
- audit entries plus warn-level log lines for admin grants (SEC-96; an out-of-band notifier is deferred to Later, 00c ruling 29);
- the quarterly restore drill (SEC-81);
- **rounds 4–6:** the state-to-audit cross-check (SEC-53), run at boot (`/readyz` 503 on a mismatch), in `verify-audit` and in `import-dataset`, which catches a database writer who lacks `HSN_AUDIT_KEY`; and restore detection through the MAC'd high-water-mark sidecar `HSN_STATE_HWM_FILE` (SEC-81), which catches a restored, replaced or rolled-back database and a deleted sidecar.

What remains (round 4 wording, SEC-53 / ruling 18): someone who holds **both** the database and `HSN_AUDIT_KEY` can still forge matching HMAC'd entries and a matching sidecar. Mitigations: keep the audit key off the DB host's backups and volumes, keep the sidecar on a different volume and backup set, and anchor the head off-host daily (`export-audit-head`, `verify-audit --head`). Dataset versions approved before schema v5 have no audited content hash and are checked by name only (`legacy`) until the next publish.

Accepted residuals from round 7 (security-code-core-round4):
- **SA-C4-03:** one admin still chooses the prefixes of a keyed manual watched row when creating it. The row cannot be resolved or narrowed without a second admin and stays `detected`, so the SLA alert fires; the worst case is a delayed warning on the real codes, not silence. The creation is HMAC-audited with its prefixes.
- **SA-C4-04:** a backup taken before the first boot of round-6 code, restored with the sidecar deleted, initialises a new sidecar silently. Runbook: after upgrading, boot once (writes `dataset.hwm_initialised`), export a fresh audit head off-host, and use older backups only after `verify-audit --head` against an export.

**Single-process limitation (SA-D-13).** v1 runs one Node process with two listeners (public, and loopback admin). That process holds the key pepper, the audit key, the LLM key and the admin writer connection. A remote-code-execution bug in a parsing dependency or in Fastify therefore reaches all of them. Mitigations:
- separate DB connections (SEC-91);
- the loopback admin listener (SEC-18);
- minimal dependencies (SEC-65).

Moving the admin plane and any signer into separate processes is planned work, not v1.

## 18. Per-file review checklist (auditor quick pass)

For each changed file, answer:

1. Does it read any request input? → schema present, limits set (SEC-24..31).
2. Does it touch SQL? → bound params, literal SQL, FTS builder used, right connection (SEC-39..42, SEC-91).
3. Does it make outbound calls? → only via `src/adapters/httpClient.ts`, only from `src/adapters/`, with its own host allow-list and budgets (SEC-32..38).
4. Does it log? → no keys, no raw names, `input_hash` keyed with `HSN_LOG_KEY`, request id present (SEC-61..63).
5. Does it touch rates, reference data or the audit log? → append-only, maker–checker on `actor_id`, approval bound to `content_sha256`, citation with PDF hash (SEC-43..56, SEC-93).
6. Does it handle errors? → problem+json, no leaks, echo only validated values (SEC-73..75).
7. Does it add a dependency or env var? → justified, validated at boot (SEC-57, SEC-65).
8. Does it involve the classifier/LLM? → external-data cap (SEC-46) and the `06-ai-restrictions.md` checklist.
9. Does it touch the admin plane? → admin listener only, no browser key, `Idempotency-Key` on every write (400 `idempotency-key-required`), audit and alertable log lines (SEC-18, SEC-45, SEC-96).
